# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js rewrite of the consumer-facing storefront + checkout flow **and** the admin CMS from `../index.html` (a self-contained static HTML tea e-commerce site — see `../CLAUDE.md` for that file's structure), backed by a real database (Cloudflare D1) instead of `localStorage`. Deployment target is Cloudflare (Workers + D1), via `@opennextjs/cloudflare`. See `TODO.md` for what's still deferred and why, and `ORIGINAL_INTEGRATIONS.md` for how the original site's order-notification flow worked (Formspree + Google Sheets — both fully replaced here by D1 + Resend).

**Explicitly not ported / not in scope**: real LINE Pay payment integration (still self-reported confirmation codes, matching the original), automated tests, and cart persistence across page reloads (cart is plain React state — a deliberate decision, not an oversight; see `TODO.md`).

## Commands

- `npm run dev` — plain Next dev server (Turbopack). Works for UI-only work, but any route touching D1 (`getCloudflareContext().env.DB`) needs the Cloudflare-aware dev flow below.
- `npm run cf:build` — `opennextjs-cloudflare build`; produces `.open-next/` and prints the full route table (useful to confirm a new route/proxy actually got bundled).
- `npm run cf:dev` — `cf:build` + `wrangler dev`; the real local dev flow — every page can read/write actual local D1 data. **Use this, not `npm run dev`, whenever working on anything that touches the database, auth, or admin.**
- `npm run cf:deploy` — build + `wrangler deploy` to Cloudflare.
- `npm run build` / `npm run start` — plain Next.js production build/start (not the Cloudflare path; mostly for quick local smoke checks).
- `npm run lint` — ESLint (flat config, `eslint-config-next` core-web-vitals + typescript).
- `npx tsc --noEmit` — type-check only (`strict: true`).
- `npm run db:generate` — `drizzle-kit generate`, produces a new migration under `drizzle/migrations/` from schema changes in `lib/db/schema.ts`.
- `npm run db:migrate:local` / `db:migrate:remote` — apply pending migrations via Wrangler (`drizzle-kit migrate` cannot talk to a D1 binding directly).
- `npm run db:seed:local` / `db:seed:remote` — apply `drizzle/seed.sql` to local/remote D1.
- `npm run db:seed:dump` — re-export the *current* local D1 directory tables (regions/products/statuses/etc., not `orders`/`order_items`/`order_failure_logs`) into a fresh `drizzle/seed.sql`, then wraps it in a transaction via `scripts/wrap-seed-transaction.mjs`. Use this after deliberately reshaping seed data locally, to make the new state reproducible.
- `npm run db:reset:local` — wipes and re-seeds the local D1 directory tables from `drizzle/seed.sql`.

No automated test runner is configured (see `TODO.md`).

## Architecture

**Everything goes through the API routes — no component or Server Component calls `lib/data.ts` / `lib/admin-data.ts` directly except the route handlers and a few Server Components that fetch via `lib/fetch-api.ts`.** `app/page.tsx`, `app/layout.tsx`, and every `app/admin/**/page.tsx` fetch their own `/api/**` routes (via an absolute URL built from request headers — `lib/fetch-api.ts#getBaseUrl`/`fetchJson`, the latter wrapped in React's `cache()` to dedupe repeated calls within one request) rather than calling the data layer inline. This keeps `lib/data.ts`/`lib/admin-data.ts` as the only two callers of the database, so a future storage change only touches those two files.

- **`lib/db/schema.ts`** — Drizzle schema for all 11 D1 tables: `regions`, `product_statuses`, `products`, `product_images`, `customer_fields` (has a soft-delete `active` flag — see below), `bundle_discounts`, `bundle_discount_products`, `orders`, `order_items`, `order_field_values`, `order_failure_logs`, `site_settings`.
- **`lib/db/client.ts`** — exports `getDb()`, called fresh inside every `lib/data.ts`/`lib/admin-data.ts` function (D1 bindings are only available per-request via `getCloudflareContext().env.DB`; there is no module-level singleton connection, unlike a typical `better-sqlite3` setup). Also documents that D1 has `PRAGMA foreign_keys = 1` on by default (unlike a bare local SQLite file) — foreign key constraints are live.
- **`lib/data.ts`** — the sole data-access layer for the consumer-facing storefront: `getRegions()` / `getProducts(region?)` / `getProductStatuses()` / `getCustomerFields()` (only returns `active: true` rows) / `getBundleDiscounts()` / `getSiteSettings()` / `createOrder(payload)`. All read from D1 via Drizzle. Call signatures are the stable public contract every route depends on.
- **`lib/admin-data.ts`** — the CRUD data layer for the admin CMS (`app/admin/**`), separate from `lib/data.ts` on purpose: `create*`/`update*`/`delete*`/`list*` functions (`listOrders`, `updateOrderStatus`, `listOrderFailures`, `updateSiteSettings`, etc.) that the consumer storefront never calls. Every write function does server-side format validation itself (throws `AdminValidationError`, mapped to a 400 by `lib/admin-api-helpers.ts#handleAdminError`) — never trust the admin UI's client-side input constraints alone. `deleteCustomerField` is a soft delete (`UPDATE ... SET active = false`, not a real `DELETE`) so existing orders' `order_field_values` never dangle; there's currently no "reactivate" API.
- **`lib/pricing.ts`** — all money math (`calcSubtotal`, `calcBundleDiscount`, `calcShippingFee`, `calcOrderTotals`). Bundle discount rule: cart must contain at least one unit of every product ID listed in a bundle; if multiple bundles qualify, only the single highest-discount one applies (no stacking). `threshold`/`fee`/`bundles` are now **required** parameters (no defaults) — callers must explicitly pass values read from `getSiteSettings()`/`getBundleDiscounts()`, so a forgotten argument is a compile error, not a silently-wrong charge.
- **`lib/db/schema.ts`'s `site_settings`** is a single generic key-value table (`key` PK, `value` text) covering both theme/appearance (`theme.scaleTitle`, `theme.colorTitle`, …) and business rules (`shipping.freeThreshold`, `shipping.fee`, `notify.shopEmail`, `branding.logoImage`, `branding.linePayQrImage`, `weightOptions`). `getSiteSettings()` returns a typed `{ theme, shipping, notify }` (plus branding/weightOptions) object with fallback defaults if a row is missing — callers never touch key-value details directly. The "棋願製造中" status-tag color is **not** in this table; it's `product_statuses.comingsoon.color`, edited via `updateProductStatus("comingsoon", …)`.
- **`app/layout.tsx`** is an async Server Component that fetches `/api/site-settings` and injects the theme values as CSS variables (`--scale-title`, `--color-title`, etc.) via an inline `<style>` tag; the relevant CSS Modules reference `var(--xxx)` instead of hardcoded values.
- **`components/Storefront.tsx`** — the client component holding cart/UI state (`"use client"`; cart, selected weights, current region, checkout/lightbox/policy modal open-state, plus `siteSettings`/`regions` passed down as props from the Server Component tree). Everything under it is presentational, threaded via props/callbacks — no Context, no global store. **Cart is not persisted** — refreshing the page clears it (deliberate, see `TODO.md`).
- **`components/CheckoutOverlay.tsx`** — remounted via a `key` (`checkoutInstance` counter in `Storefront.tsx`) each time it's opened, instead of resetting its internal form state in a `useEffect` (that pattern trips the `react-hooks/set-state-in-effect` ESLint rule and is the idiomatic React fix — don't reintroduce the effect-based reset). Same pattern applies to `LinePayQrModal`/`BankTransferModal`, which are now conditionally rendered (`{open && <Modal .../>}`) rather than always-mounted with an internal `if (!open) return null`, so their input fields (`last3`/`last5`) don't retain stale values across opens.
- **Cart total display excludes shipping.** `Cart.tsx` shows `subtotal − bundleDiscount` as "總計"; the shipping fee only appears in the shipping-notice text and gets added into the total at checkout (`totals.total` from `calcOrderTotals`, used in `CheckoutOverlay`/`OrderCompleteOverlay`). This matches `../index.html`'s `renderCart()` exactly — don't "fix" the cart display to include shipping, that would be a regression, not a bug fix.
- **`POST /api/orders`** (`app/api/orders/route.ts` → `lib/data.ts#createOrder`) — validates the full order (empty cart, per-field required/format checks — `lineId` is only required once the cart qualifies for free shipping, mirroring the original's conditional-visibility rule — CVS store name, gift recipient name, payment confirmation code — plus any non-builtin `customer_fields`, collected in `customFieldValues`). On success, writes `orders`/`order_items`/`order_field_values` atomically via `db.batch(...)` (D1's HTTP-based API has no interactive transactions), then fires `lib/email.ts#sendOrderNotification()` **without awaiting it** (fire-and-forget, `.catch()` only logs — an email failure never fails the order). If the `db.batch` write itself fails, a row is written to `order_failure_logs` (error message/stack/payload snapshot) before re-throwing, so the client still gets a failure response — this is for *system* failures, not validation errors (empty cart etc. still just return 400, unlogged).
- **Admin auth** — single admin password, no next-auth. `lib/auth.ts` does PBKDF2 (100k iterations, Web Crypto only, no added dependency) for password hashing, and a hand-rolled HMAC-SHA256 signed cookie (`qw_admin_session`, httpOnly, 7-day expiry) — no JWT library. Password check order: DB override (`site_settings` key `auth.adminPasswordOverride`, hashed, set via "change password" in the admin settings page) first, then plaintext `ADMIN_PASSWORD` env var as the fallback default. **`proxy.ts`** (Next.js 16's renamed `middleware.ts` — the file must be named `proxy.ts` and export `proxy()`, not `middleware()`) guards `/admin/:path*` and `/api/admin/:path*`; `app/admin/(protected)/layout.tsx` also re-checks the session server-side as defense-in-depth. Login/logout/change-password live outside the `(protected)` route group so the login page doesn't inherit the admin nav.
- **Images** live under `public/images/` (`regions/`, `products/`), decoded from the base64 embedded in the original `index.html`; not migrated to object storage (R2 was ruled out — see `DEPLOYMENT.md`/plan history — because it requires binding a payment method to the Cloudflare account even within the free tier). New product/region photos are added via the admin UI as a **plain URL field** (store owner uploads elsewhere, pastes the link) rather than a file upload.
- **RWD breakpoints are `<480px` / `480–800px` / `≥800px`**, intentionally redesigned rather than copied from the original (which only had two inconsistent breakpoints at 760px and 800px for background-image and layout respectively — a real gap, not a stylistic choice). Desktop (`≥800px`) uses a two-column layout with a `position: sticky` cart.

## Cloudflare / D1 specifics worth knowing before touching data-layer code

- **No singleton DB connection.** Always call `getDb()` inside the function that needs it; never hoist a client to module scope — it won't have a binding outside a request.
- **`db.batch([...])`, not interactive transactions.** D1's HTTP API doesn't support `BEGIN`/`COMMIT` across round-trips from application code; multi-statement atomic writes go through `db.batch()`.
- **Local dev needs `wrangler dev`** (via `npm run cf:dev`), not plain `next dev`, for anything touching `getCloudflareContext()`. Plain `next dev` works for pure UI iteration on components that only receive props.
- **Secrets** (`RESEND_API_KEY`, `EMAIL_FROM`, `ADMIN_PASSWORD`, `SESSION_SECRET`) are Cloudflare `vars`/`secrets` (`wrangler secret put ...` in production, `.dev.vars` locally — gitignored, copy from `.env.example`), never rows in `site_settings` — that table is only for non-sensitive, admin-editable values.
